# Sherlock AI — Product & Technical Specification 1.0

**Статус документа:** базовая фиксация объёма релиза  
**Целевая версия:** 1.0.0  
**Рабочая ветка:** `refactor/secure-local-assistant-foundation`  
**Правило:** в 1.0 входят только перечисленные ниже функции и исправления, необходимые для их надёжной работы.

## 1. Цель релиза

Выпустить стабильного персонального локального ИИ-ассистента для Windows. Пользователь должен установить приложение, подключить локальную модель Ollama, вести диалоги, сохранять полезный контекст, пользоваться личным рабочим пространством и безопасно применять ограниченную Telegram-интеграцию.

Релиз 1.0 — полезный законченный продукт, а не обещание реализовать все возможные функции ИИ-агента.

## 2. Целевой пользовательский сценарий

1. Пользователь устанавливает приложение и запускает его без ручной настройки Python.
2. Приложение проверяет окружение и объясняет, если Ollama или модель недоступна.
3. Пользователь выбирает установленную локальную модель и общается с ней в чате.
4. Диалоги и рабочие данные сохраняются между запусками.
5. Пользователь может вести задачи, заметки, просматривать план дня и использовать фокус-сессию.
6. Ассистент использует только разрешённую пользователем память и доступные локальные файлы.
7. Telegram подключается отдельно и только после явной авторизации. Подготовленный ответ не отправляется без подтверждения пользователя.

## 3. Обязательный объём 1.0

### 3.1. Windows Desktop и установка
- Основной продукт 1.0 — Windows desktop.
- Сборка приложения в распространяемый пакет.
- Первый запуск, понятные ошибки и проверка окружения.
- Корректное закрытие приложения и сохранение данных.
- Установка и запуск без предварительно установленного Python у конечного пользователя.
- Документация по установке, обновлению и резервному копированию.

### 3.2. Чат и модели
- Локальная генерация через Ollama.
- Обнаружение доступных моделей и выбор модели.
- Потоковый вывод ответа.
- Новый диалог, история, открытие и удаление диалогов.
- Обработка остановки генерации, недоступности Ollama и ошибок модели.
- Настройки стиля ответа, если они доступны в текущей реализации.

### 3.3. Рабочее пространство
- Создание, изменение, завершение и удаление задач.
- Заметки: создание, просмотр, изменение и удаление.
- Обзор дня и фокус-сессия.
- Сохранение состояния в локальной SQLite после перезапуска.
- Подтверждение перед необратимым удалением.

### 3.4. Память
- Явное сохранение фактов пользователем.
- Просмотр, изменение и удаление сохранённых фактов.
- Использование релевантной памяти в контексте диалога.
- Понятное различие между историей чатов, заметками и долговременной памятью.
- Пользовательский контроль над тем, что сохраняется.

### 3.5. Локальные файлы
- Выбор разрешённых пользователем папок.
- Поиск файлов и просмотр недавних файлов.
- Предпросмотр и анализ поддерживаемых форматов.
- Ограничения размера/формата и понятные сообщения об ошибках.
- Не выполнять содержимое файлов как код или инструкции.

### 3.6. Telegram (условный модуль релиза)
- Авторизация личного аккаунта через Telethon/MTProto.
- Поддержка IPv6 для сетей, где IPv4-маршрут недоступен.
- Проверка сессии и понятная диагностика подключения.
- Обработка только явно разрешённых контактов/сценариев.
- Создание, просмотр, редактирование и отмена черновиков.
- Отправка только после отдельного подтверждения пользователя.
- Без массового чтения истории и без скрытой обработки чужих переписок.

Telegram включается в стабильный релиз только после успешного живого теста с новой, безопасно созданной сессией. Если живой тест не пройден, Telegram-модуль выключается в релизной сборке, а desktop-продукт выпускается без него; релиз 1.0 не блокируется бесконечно.

### 3.7. Безопасность и надёжность
- Секреты и сессии не попадают в Git, логи, диагностические отчёты и артефакты сборки.
- Запрет на произвольное выполнение команд/кода моделью.
- Явное подтверждение внешних действий.
- Минимально необходимые разрешения.
- Безопасное хранение локальных данных и документированное предупреждение, если SQLite не зашифрована.
- Резервное копирование и восстановление пользовательских данных.
- Обработка повреждённой/отсутствующей базы и ошибок записи.


### 3.8. Фоновые операции и завершение приложения
- Фоновые задачи запускаются через единый менеджер, который отслеживает состояние, результат и ошибку.
- Для поддерживающих отмену задач используется cooperative cancellation; UI не управляет потоками напрямую.
- Закрытие приложения запрещает запуск новых задач, отправляет сигналы отмены активным workers и ожидает завершения перед закрытием event bus и UI.
- Завершённые task handles очищаются; длительные сессии не должны накапливать завершённые потоки в памяти.
- Worker-потоки не обращаются к Tkinter напрямую: результаты и ошибки доставляются через event bus.

## 4. Не входит в 1.0

- Мобильные приложения.
- Полноценный web-клиент (отдельная версия после стабилизации desktop).
- Голосовой ассистент и постоянное прослушивание.
- Автономное управление мышью/клавиатурой и произвольным ПО.
- Самостоятельная отправка сообщений без подтверждения.
- Автоматическое обучение базовой языковой модели.
- Мультиагентная система.
- Облачная синхронизация между устройствами.
- Магазин плагинов и неограниченные внешние интеграции.
- Автоматическое выполнение произвольного кода и shell-команд.

Новые идеи записываются в post-1.0 backlog и не меняют объём релиза.

## 5. Нефункциональные требования

- Поддерживаемая ОС: Windows 10/11 x64 (финальная матрица подтверждается на тестовых машинах).
- Не требовать дискретную видеокарту: модель выбирается под ресурсы конкретного компьютера.
- Не предполагать, что одна модель подходит всем устройствам; тяжёлые модели не должны быть обязательными.
- UI не должен зависать во время генерации или файловых операций.
- Пользовательские данные переживают перезапуск и обновление приложения.
- Критические операции сопровождаются понятной обратной связью.
- Все ключевые сценарии покрываются автоматическими тестами или воспроизводимым ручным тест-кейсом.

## 6. Критерии приёмки 1.0

Релиз допускается, если одновременно выполнено:
1. Установщик/пакет запускается на чистой Windows-машине без Python.
2. Первый запуск и диагностика работают.
3. Ollama обнаруживается; выбор модели и чат работают.
4. История диалогов сохраняется и восстанавливается.
5. Задачи, заметки, обзор дня и фокус-сессия проходят сквозные сценарии.
6. Память сохраняется, используется и удаляется по команде пользователя.
7. Поиск/предпросмотр файлов работают на поддерживаемых форматах.
8. Данные не теряются после перезапуска и обновления.
9. Telegram либо проходит отдельный живой тест и включается, либо явно отключён в сборке 1.0.
10. Автоматические тесты и Windows build pipeline проходят.
11. Нет открытых blocker/critical дефектов.
12. README, руководство пользователя, политика хранения данных и release checklist актуальны.
13. Создан Git tag `v1.0.0` и опубликованы release notes.

## 7. Определение готовности задачи

Задача считается DONE только если:
- код интегрирован в целевую ветку;
- критерии приёмки задачи проверены;
- тесты добавлены/обновлены и проходят;
- пользовательская документация обновлена, если сценарий изменился;
- нет известного критического регресса.

Наличие файла или функции в репозитории само по себе не доказывает, что функция готова.

## 8. Управление объёмом

- В 1.0 не добавляются новые продуктовые модули после фиксации этого документа.
- Разрешены исправления дефектов, безопасность, производительность и завершение уже перечисленных сценариев.
- Любое расширение объёма переносится в `POST_1_0_ROADMAP.md`.
- Не переделывать работающий модуль без воспроизводимого дефекта или измеримого улучшения.
- После выполнения release checklist объём 1.0 закрывается.

## 9. Версии после 1.0

- **1.1:** улучшения на основании реального использования, удобство, надёжность и небольшие интеграции.
- **1.2:** расширенные автоматизации с разрешениями и журналом действий.
- **1.3:** голос и дополнительные мультимодальные возможности.
- **2.0:** web-клиент/синхронизация/агентные сценарии — только после отдельного проектирования и оценки безопасности.

Номер версии не является обещанием даты или обязательного состава: каждая версия получает отдельный ограниченный scope и критерии приёмки.
